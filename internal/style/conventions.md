# 태스크 작성 규약

이 규약의 짧은 사실 메모 제한은 `executor: human` 작업에 적용한다. 같은 vault의
`executor: agent` 작업은 에이전트의 실제 작업 기록용이다. 착수 전 목표·실행
단계·완료 기준을 note에 적고, 진행 중 실제 결과와 검증 근거를 시각이 붙는
`task_note`로 누적한다. MCP `vault_info`가 `mode: shared`인지 확인한다.

이 vault 의 태스크는 3주 뒤의 **사람**이 읽는다. 티켓이 아니라 할 일 한 줄이다.
읽는 사람은 하나뿐이고, 그 사람은 이미 맥락을 절반쯤 잊은 상태다.

## 한 줄 원칙

**사용자가 쓴 어휘를 그대로 옮긴다. 요약하거나 격식체로 고쳐 쓰지 않는다.**

"이거 A팀한테 물어봐야 됨" 을 "A팀과의 사전 협의를 통한 요구사항 확정 필요" 로
바꾸면 뜻은 같지만 내가 쓴 글이 아니게 된다. 남는 건 읽기 싫은 목록이다.

## 필드별

문장을 쓰는 자리는 셋뿐이다. 나머지(project, priority, scheduled, due,
estimate, tags, links)는 필드이므로 문장에 섞지 않는다.

### title — 명사구 한 줄, 40자 안쪽

- 동사 종결(`~한다`, `~하기`, `~필요`)을 쓰지 않는다. 무엇에 대한 일인지만 쓴다.
- 한 제목에 두 가지를 묶지 않는다(`및`, `그리고`). 두 가지면 태스크도 둘이다.
- 대괄호 접두, 티켓 번호, 프로젝트 이름은 제목이 아니라 필드다.
- 고유명사를 지우지 않는다. 클러스터가 셋이면 어느 것인지가 제목의 전부다.
- 끝을 알 수 있게 쓴다. 언제 완료를 누를지 모르는 제목은 영원히 이월된다.

```
나쁨  k8s 클러스터 노드 풀 업그레이드를 위한 사전 영향도 분석 및 롤백 계획 수립
중간  노드 풀 업그레이드 사전 점검          ← 어느 클러스터인지가 없다
좋음  game-prod 노드 풀 1.29 업그레이드 점검

나쁨  클라우드 비용 최적화 관련 검토
중간  GCP 비용 검토                         ← 언제 끝나는지 알 수 없다
좋음  GCP 9월 청구서 급증분 원인 확인
```

### note — 평문 2~4줄

첫 줄은 "왜 지금 이게 목록에 있는가". 나머지는 사실(날짜·수치·사람·링크)이다.

- 헤딩(`##`)·체크박스·번호 목록을 쓰지 않는다. **거부된다.**
- 계획·단계·수용 기준은 태스크가 아니라 저장소 문서에 둔다. 할 일이면 태스크로 쪼갠다.
- 앞으로 할 일이 아니라 지금 아는 사실을 적는다.
- 모르는 것은 모르는 채로 적는다. "재현은 아직 한 번뿐" 이 나중에 쓸모가 있다.
- 제목의 부연이면 차라리 비워 둔다.

```
나쁨
## Context
현재 task_add 호출 시 중복 태스크가 생성될 수 있는 문제가 있습니다.
## Approach
1. Sync 타이밍 조사  2. 채번 로직 수정  3. 테스트 추가
## Acceptance Criteria
- [ ] 회귀 테스트 통과

중간
task_add 동시 호출 시 중복 생성 이슈. 원인으로 추정됨. 테스트 추가가 필요함.
  ← 구조는 없앴지만 문체가 보고서고, "테스트 추가" 는 사실이 아니라 계획이다

좋음
9/12 Codex 세션에서 같은 태스크가 두 번 생겼다.
begin() 의 Sync 보다 채번이 먼저 도는 것 같다. 재현은 아직 한 번뿐.
```

### blocked_reason — 누구를 언제까지 기다리는지 한 줄

```
나쁨  외부 의존성으로 인한 대기
중간  A팀 회신 대기                          ← 언제 쪼아야 할지 모른다
좋음  A팀 스펙 대기 — 9/12 요청, 18일까지 준다고 함
```

선행이 태스크로 존재하면 사유가 아니라 `blocked_by` 를 쓴다. 그래야 선행이
끝날 때 자동으로 풀린다.

### task_note — 그때 안 사실 한 문장

통화 내용, 확인한 수치처럼 나중에 근거가 될 것을 그 순간에 적는다.
시각이 함께 쌓이므로 "오늘", "방금" 같은 말은 필요 없다.

```
나쁨  진행 상황을 지속적으로 모니터링 중
중간  모니터링 중, 아직 이상 없음            ← 무엇을 봤는지가 없다
좋음  2시간 부하 돌림. p99 180ms, 에러 0

나쁨  관련 담당자와 논의 완료
좋음  B팀 담당자: 이번 스프린트엔 못 본다고. 10월 첫 주에 다시 물어보기로
```

지금 하지 않을 아이디어는 태스크 메모가 아니라 다른 곳에 남긴다. "검토 필요"
로 끝나는 메모는 아무도 다시 읽지 않는다.

## 중간과 좋음을 가르는 네 가지

1. 고유명사가 남아 있는가 — 어느 클러스터, 누구, 어느 파일
2. 숫자가 남아 있는가 — 날짜, 시각, 측정값, 기한
3. 계획이 아니라 사실인가
4. 3주 뒤의 내가 이 줄만 보고 다음 행동을 정할 수 있는가

1~3 은 도구가 경고까지 해 준다. 4 는 사람만 판단할 수 있고, 규약이 존재하는
이유다.
