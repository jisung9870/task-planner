# task-planner 기획서

```
독자        본인 (3개월 뒤 재개 시점의 자신 포함)
목적        개인 업무를 md 파일 SSOT로 관리하는 터미널 네이티브 도구의 범위·구조 확정
대상 환경   로컬 macOS (darwin/arm64), 단일 사용자
최종 검토   2026-09-12
부분 수정   2026-09-26 (에이전트 실행 기록), 2026-10-03 (실행 agent·모델 등급 지정),
            2026-10-03 (시간 관리: 계획 대신 기록)
다음 검토   7일 시범 사용 종료 시점 또는 2026-11-12 중 빠른 쪽
상태        확정 — P0·P1 구현 완료, P2 일부 선반영. 시간 관리 개정 반영(2026-10-03)
```

## 구현 상태 (2026-09-12)

구현은 Go + Bubble Tea 로 진행했고 저장소 루트에서 `make build` 로 `./tp` 가 나온다.
계층 규칙과 함정은 `CLAUDE.md`, 사용법은 `README.md` 에 있다.

| 단계 | 상태 | 비고 |
|---|---|---|
| P0 | 완료 | Today/Week/Projects/All, 상태 전이, 빠른 캡처, CLI, JSON 인덱스 |
| P1 (1~6번) | 완료 | 편집기 연동·롤오버·주간 리포트·git 자동 커밋·watcher·질의 DSL |
| P2 (7~11번) | 완료 | 의존성 자동 해제·시간 추적·반복·칸반 보드·WIP 경고 |
| P2 (12번 아카이브) | 완료 | `tp archive` — 기본 30일, 분기별 샤딩, dry-run |
| P2 (13번 MCP) | 완료 | stdio 서버 (`tp mcp`), 읽기 10종 + 쓰기 10종(가져가기·놓기 포함), 삭제 미제공, 사람용 작성 규약 검사. `day_load`·`rollover` 는 2026-10-03 퇴역 |
| P2 (14~16번) | 미착수 | Jira 연동, 컨텍스트 태그, 스탠드업 |
| P3 (20번 FTS) | 부분 | `body:` 질의로 본문 검색. 인덱스가 아니라 파일을 읽는다 (SQLite 전환 없이) |
| P3 (17~19번) | 미착수 | 캘린더 export, 알림, HTTP API |

기획서에 없던 것 중 쓰면서 필요해진 것들도 들어갔다. **진행 기간**
(`scheduled`~`due` 를 한 덩어리로 읽고 Week 그리드에 걸쳐 그림), **하루 용량**
(`daily_capacity` 대비 배정 시간), **되돌리기**(파일 pre-image 기반, 한 동작 =
한 단계), **다중 선택 일괄 처리**, **저장된 뷰**, **다음 할 일 추천**, 프로젝트
생성·마일스톤, 한 줄 메모. 자세한 조작은 `README.md`.
이 중 진행 기간과 하루 용량은 2026-10-03 개정에서 걷어냈다(아래).

**시간 관리: 계획 대신 기록 (2026-10-03 개정, 반영됨).** task 는 "무엇을 할지"의
단위로 두고, 마감·예상 소요를 미리 정하지 않는다. 대신 언제 착수했고 언제 끝났는지를
기록해 "얼마나 걸렸나"를 사후에 본다. `due`·`estimate` 입력을 없애고, `scheduled` 는
"Today 에 꺼낼 날"로 뜻을 좁히고, 우선순위는 그대로 둔다. 근거와 규칙은 데이터 모델의
"시간: 계획이 아니라 기록" 절. 이 절과 충돌하는 아래 서술은 그 절이 우선한다.

**agent 가 쓴 태스크의 문장.** MCP 로 캡처하면 제목이 길어지고 메모가 문서가
된다 — 모델은 맥락을 빠짐없이 적는 쪽이 안전하다고 보기 때문이다. 그런데 이
vault 를 읽는 사람은 하나뿐이고, 읽기 싫은 목록은 결국 안 읽는 목록이 된다.
그래서 쓰기 도구에 규약 검사를 뒀다. 구조(헤딩·체크박스·단계 계획)는 거부하고
어투는 경고만 한다 — 어투를 거부하면 모델이 고쳐 쓰다 수렴하지 못하고, 캡처가
막히면 도구 자체를 안 쓰게 된다. 규약 전문은 `internal/style/conventions.md`
이고 MCP 리소스 `tp://conventions` 로도 읽힌다.

**에이전트 실행 기록 (2026-09-26 개정).** 사람과 에이전트 작업은 기본 vault
하나에 두고 `executor: human|agent`로 구분한다. 프로젝트는 함께 집계한다.
에이전트 태스크에는 착수 전에 목표·실행 단계·완료 기준을 적고, 진행 중 실제
수행 내용과 검증 결과를 시각이 붙는 메모로 남긴다. 짧은 사실 메모 규칙은
`executor: human`에만 적용한다. TUI의 `F`는 사람·agent·전체를 순환한다.
에이전트가 올바른 vault에 연결됐는지는 MCP `vault_info`로 확인한다. 세션 강제
종료 뒤 진행중 상태는 살아 있는 실행의 증거가 아니므로 재개 시 실제 상태를
확인한다. 여러 프로세스의 동시 쓰기는 별도로 검증되기 전까지 사용 범위에서 뺀다.

**실행 agent·모델 등급 (2026-10-03 개정).** 등록할 때 누가 할 일인지(`agent`)와
얼마나 무거운 일인지(`tier`)를 적을 수 있다. 실행기는 이 도구에 넣지 않는다 —
값만 원천으로 두고, 판단과 실행은 이 값을 읽는 쪽이 한다. 상세는 데이터 모델의
"실행 agent 지정과 가져가기" 절. 여러 프로세스의 동시 쓰기 중 **가져가기(claim)
하나만** vault 잠금으로 보호한다. 나머지 쓰기는 여전히 위 제약을 따른다.

**남은 검증 하나.** 7일간 실제 업무를 이 도구만으로 관리해 누락 0건을 확인하는
P0 합격 기준은 아직 통과하지 않았다. 기능이 아니라 이 시범 사용이 다음 관문이다.

## 결론 3줄

- **md 파일 1개 = 태스크 1개를 SSOT**로 두고, JSON 인덱스는 언제든 버리고 재생성 가능한 파생물로 분리한다.
- **DB는 지금 넣지 않는다.** Docker Postgres는 이 단계에서 순손실이고, SQLite도 P2 이후 조건부다 — 판단 근거와 전환 트리거는 "DB 판단" 절에 있다.
- **Appetite 2주**로 P0를 끊고, 그 안에 안 들어가는 건 전부 P1 이후로 민다.

## 한 줄 정의

터미널에서 오늘·이번 주 할 일과 그 상태를 보고 바꾸되, 데이터는 사람과 AI가 직접 읽고 쓸 수 있는 markdown 파일로 남는 개인 업무 관리 TUI.

## Problem — 해결하려는 문제

추상적 "생산성"이 아니라 실제로 답하고 싶은 질문들이다. 이 목록이 이후 기능 우선순위의 판단 기준이 된다.

| 답하고 싶은 질문 | 지금 무엇이 불편한가 |
|---|---|
| 오늘 뭘 해야 하지? | 할 일이 Jira, 슬랙 스크롤, 메모 앱, 머릿속에 흩어져 있다 |
| 이번 주에 뭘 했고, 각각 언제 시작해 얼마나 걸렸지? | 끝난 뒤에는 착수 시점이 남지 않아 소요를 기억으로 추정한다. 미리 적은 예상치는 맞춰볼 실측이 없어 교정되지 않는다 |
| 지금 꺼내 둔 것 중 뭐부터 하지? | 할 일이 전부 같은 무게로 보인다. 순서는 우선순위로, 아직 안 꺼낼 일은 꺼낼 날로 가린다 |
| 저건 왜 아직도 보류지? | 보류 사유와 해제 조건이 기록되지 않아 보류 항목이 좀비로 남는다 |
| 이 프로젝트에서 내가 진행 중인 게 뭐지? | 태스크와 프로젝트 문서가 다른 도구에 있어 연결이 끊긴다 |
| 지난주에 내가 뭘 했지? | 주간보고를 쓸 때마다 기억과 커밋 로그를 역추적한다 |

동반 문제: 기존 도구 대부분이 자체 포맷을 쓰기 때문에, Claude Code 같은 에이전트가 내 업무 상태를 읽거나 갱신할 수 없다.

## Appetite

**P0 = 2주.** 고정 기간 + 유동 범위로 운영한다. 2주에 안 들어가면 기능을 줄이지 기간을 늘리지 않는다.

## 사용자와 사용 맥락

혼자 쓴다. 여는 순간은 셋이다.

1. **아침 (2분)** — 터미널 열고 `tp`. 오늘 할 일 확인, 순서 정함.
2. **작업 중 (5초)** — 뭔가 떠오르면 잊기 전에 캡처. 상태를 진행중→완료로 넘김. **여기서 3초 넘게 걸리면 도구를 안 쓰게 된다.**
3. **금요일 (10분)** — 이번 주 완료분 훑고 주간보고 초안 뽑음. 못 끝낸 것 다음 주로 이월.

맥락이 결정하는 것: 항상 터미널에 떠 있어야 하므로 **콜드스타트가 빨라야 하고(목표 100ms 이내), 외부 데몬에 의존하면 안 된다.**

## 목표 / 비목표

**목표**
- md가 유일한 원천. 도구가 사라져도 데이터는 에디터로 읽힌다.
- 상태(대기중/진행중/보류/완료)와 프로젝트 연관이 한 화면에서 보인다.
- TUI 없이 CLI만으로도 캡처·완료 처리가 된다.
- 향후 API/MCP를 붙일 때 도메인·저장 계층을 재작성하지 않는다.

**비목표 (이번에 명시적으로 안 함)**
- 다중 사용자, 권한, 인증
- 실시간 동기화와 충돌 병합 — git으로 충분하다
- 웹 UI, 모바일 앱
- Jira 대체 — 팀 워크플로우는 Jira에 남고 이 도구는 그 위의 개인 레이어다
- 자연어 일정 파싱 고도화 ("다음 주 화요일 오후") — P2에서 재검토
- 서버 상주 프로세스

## 기존 대안과 차별점

| 도구 | 왜 안 맞는가 |
|---|---|
| Taskwarrior | 기능은 충분하나 자체 바이너리 포맷 + 자체 DB라 md로 관리 불가, 메모·문서가 분리됨 |
| todo.txt | 한 줄 포맷이라 긴 작업 메모·결정 기록을 담을 수 없음 |
| Obsidian Tasks | md 기반은 맞으나 GUI 앱 상주 필요, 터미널 워크플로우와 분리 |
| org-mode | 요구를 거의 다 만족하지만 Emacs 종속 |
| dooit 등 TUI 칸반 | 자체 포맷, 프로젝트 연관·리포트 약함 |
| Jira | 팀 단위 도구. 개인 일과 관리엔 무겁고 오프라인 불가 |

**차별점 두 가지.** (1) md SSOT라서 에디터·git·AI 에이전트가 전부 1급 클라이언트가 된다. (2) 향후 MCP 서버 모드로 Claude Code가 직접 업무 상태를 읽고 쓴다 — 위 어느 도구도 제공하지 않는다.

## 핵심 기능 (P0)

각 항목은 위 Problem 표의 질문에 대응한다. 대응이 없으면 뺐다.

| 기능 | 대응 질문 | 내용 |
|---|---|---|
| Today 뷰 | 오늘 뭘 해야 하지 | 진행중 + 꺼낼 날(`scheduled`)이 오늘 이전인 대기중 + 오늘 완료. 우선순위순. 상태별·프로젝트별 그룹 전환 |
| Week 뷰 | 이번 주 뭘 했지 | 요일 컬럼에 그날 진행한 일(진행중 구간)과 끝낸 일, 다가오는 꺼낼 날 + 미배정 백로그 |
| Timeline 뷰 | 이 일이 언제 시작해 언제 끝났지 | 태스크당 한 줄의 간트. 상태 변경 로그의 실제 진행중 구간만 그린다 |
| 상태 전이 | 저건 왜 보류지 | 대기중/진행중/보류/완료/취소. **보류는 사유·해제조건 없이 저장 불가** |
| 빠른 캡처 | 잊기 전에 적기 | `a` 한 키 또는 `tp add "..."`, 필드는 나중에 채움 |
| 프로젝트 연관 | 이 프로젝트 진행분 | 태스크의 `project` 필드로 참조, 프로젝트 뷰에서 역참조 |
| 인덱스 자동 동기화 | — | md 변경 감지 후 변경분만 재파싱, 인덱스 손상 시 전체 재생성 |
| CLI 서브커맨드 | — | `tp today`, `tp add`, `tp done` — 스크립트·쉘 함수에서 호출 |

"취소"를 완료와 별도로 둔 이유: 둘을 합치면 완료 통계가 왜곡돼 회고가 쓸모없어진다.

Timeline은 실제 작업만 그린다(2026-10-03 개정). 예정 일정(`scheduled`~`due`)
모드와 `f` 전환은 없앤다. 실제 작업은 본문 상태 변경 로그의 진행중 구간과 완료·취소
시점을 사용한다. 착수 시각을 소급 입력한 일은 그 시각부터 그린다.
중단·재개 구간을 보존하고, 선택한 작업의 첫 시작과 마지막 종료 시각을 분 단위로
표시한다. `z`로 일 단위·주간 보기와 시간 단위·24시간 보기를 전환한다.
24시간 보기는 실제 작업의 하루 00:00~24:00를 표시하며, 하루씩 이동하고 오늘로
복귀할 수 있다. 진행중 구간은 현재 시각까지만 그리며 같은 날의 중단·재개를
분리한다.
로그가 없는 과거 작업은 `started_at`과
`completed`만 보조로 사용하며, 알 수 없는 시각은 추정하지 않는다. 보기 선택은
재시작 후 복원한다. 완료 조건은 날짜 없는 작업의 실제 기록 표시, 보기 전환,
중단·재개·재완료 검증이다.

All 목록은 완료 항목을 완료일 최신순으로 최대 30개만 표시한다. 검색 필터를
적용할 때는 전체 태스크에서 먼저 찾은 뒤 완료 항목 30개 제한을 적용해 오래된
완료 항목도 검색할 수 있다. Today·All의 목록 묶음은 상태별 → 프로젝트별 →
프로젝트 안에서 상태별 순서로 전환한다. 이 제한은 TUI 표시 범위에만 적용하며
태스크 원본이나 CLI 조회·리포트에는 영향을 주지 않는다.

## 추가하면 좋을 기능

P0에는 없지만 값이 확인된 것들이다. 우선순위는 "P0 못 쓰게 만드는 불편을 없애는 것"이 위다.

| # | 기능 | 왜 필요한가 | 단계 |

상태 전이 이력은 본문 `## Log` 섹션에 남긴다. frontmatter 배열로 넣으면 diff가 지저분해지고, 별도 이벤트 파일로 빼면 md가 더 이상 SSOT가 아니게 된다.

### 시간: 계획이 아니라 기록 (2026-10-03 개정)

**바꾸는 이유.** task 는 "무엇을 할지"의 단위다. 언제까지 할지, 몇 시간 걸릴지는
미리 정해도 맞지 않았고 맞춰보지도 않았다. 2026-10-03 vault 실측
(사람 작업 88건, agent 작업 247건):

| 필드 | 사람 작업에서 쓰인 정도 | 판단 |
|---|---|---|
| `due` | 88건 중 3건 | 안 쓴다. 뺀다 |
| `estimate` | 75건 입력. 그러나 완료 57건의 `actual` 은 10분 미만 27 · 없음 19 · 1시간 이상 0 | 비교 대상이 없어 교정이 한 번도 성립하지 않았다. 뺀다 |
| `scheduled` | 53건. 열린 일에서는 R4-0 10/19 → R4-1 10/20 → R4-2 10/22처럼 순서와 미룸에 쓴다 | 마감이 아니라 "아직 꺼내지 않음"으로 쓰고 있다. 뜻을 좁혀 남긴다 |
| `priority` | 85건 | 남긴다 |
| `rollover_count` | 0건 (전체에서 3건) | 퇴역 |

agent 작업은 이미 이 모델이다. scheduled·due 0건, `actual` 200건이다.

**바꾸지 않으면 안 되는 것 — 착수 기록의 품질.** `actual` 이 짧은 이유는 일이 짧아서가
아니다. 끝낼 무렵 진행중을 누르고 곧바로 완료를 누른다(완료 57건 중 50건이 진행중을
거쳤는데 1시간 이상 기록이 0건, 7건은 대기중에서 바로 완료). 반대로 끄는 걸 잊으면
8h 상한에 걸린다(`executor` 미기재 과거 작업에서 9건, #156은 88시간으로 보였다). 시간을 핵심 지표로 올리면 이 오차가 그대로 결론이 되므로,
**입력 필드를 빼는 것과 착수 시각을 바로잡는 장치는 한 묶음으로 낸다.**

**남기는 값과 뜻.**

| 값 | 뜻 | 누가 정하나 |
|---|---|---|
| `priority` | 꺼낸 일 사이의 순서 | 사람 (미리) |
| `scheduled` | 꺼낼 날. 이날부터 Today 에 보인다. 비우면 백로그. 마감이 아니므로 지나도 경고하지 않는다 | 사람 (선택) |
| 착수 시각 | 처음 진행중이 된 시각. 로그의 첫 `→ doing` 또는 소급 기록 | 기록 |
| 완료 시각 | 마지막 `→ done` | 기록 |
| 걸린 기간 | 완료 시각 − 착수 시각. 달력 기준, 중단 포함 | 계산 |
| 작업 시간 (`actual`) | 진행중 구간의 합, 구간마다 `session_cap` 상한 | 계산 |

"얼마나 걸렸나"의 기본 답은 **걸린 기간**이다. 일시정지나 타이머 방치에 덜 흔들리고,
"언제 시작해 언제 끝났나"라는 질문에 바로 대응한다. 작업 시간은 보조로 함께 보인다.
두 값 모두 로그에서 다시 계산할 수 있으므로 인덱스 불변식(파생물만 둔다)을 지킨다.

**착수 시각 소급.** 사람 작업을 완료 처리할 때 착수 기록이 없거나 진행중 구간이 `backfill_under`
(기본 10분)보다 짧으면, 언제 시작했는지 한 번 묻는다.

- TUI: `오늘 오전 / 어제 / 시각 입력 / 건너뜀` 선택. 건너뛰면 지금처럼 기록한다.
  질문 하나로 끝나야 한다 — 3초 규칙(사용 맥락 2번)을 넘기면 완료 처리를 미루게 된다.
- CLI: `tp done <ref> --since 10:30` (`--since yesterday`, `--since 2026-10-01T14:00`).
- MCP: `task_status` 에 선택 인자 `since`. agent 는 보통 `start: true` 로 등록하므로
  묻지 않는다.
- 기록은 로그에 덧붙인다. 과거 줄을 고치지 않는다:
  `- 2026-10-03 12:28 todo → done (착수 소급 10:30) [+1h58m]`.
  계산은 소급 시각을 착수로 읽는다. 로그를 시간순으로 다시 쓰지 않는 이유는 diff 와
  되돌리기가 "한 동작 = 덧붙인 한 줄"이라는 전제에 기대기 때문이다.

**"잘못 쪼갠 태스크" 신호.** 롤오버 이월 횟수 대신 기록에서 읽는다.
꺼낸 날로부터 N일 동안 착수하지 않음(쪼개거나 버릴 후보), 진행중 N일째(너무 큰 일).
N은 config, 기본 5일. Today 와 다음 할 일 추천의 이유에 표시한다.

**걷어내는 것.**

| 대상 | 처리 |
|---|---|
| 입력: TUI 추가·편집, CLI `--due`·`--estimate`, `tp set` | 제거 |
| MCP `task_add`·`task_edit` 의 `due`·`estimate` | 한 버전 동안 받아 저장하되 폐지 경고를 돌려준다. 그 뒤 제거. 오래된 skill 을 쓰는 agent 가 바로 실패하지 않게 하려는 것 |
| 정렬 (`SortDefault`) | 상태 → 우선순위 → 꺼낼 날 → id. 마감 초과·마감 순 제거 |
| 다음 할 일 추천 이유 | "마감 N일 초과·D-N·N회 이월" 제거. "꺼낸 뒤 N일 미착수·진행중 N일째" 추가 |
| Today | `due <= 오늘` 조건 제거 |
| Week | 마감 임박·하루 용량 제거. 요일별로 그날 진행한 일과 끝낸 일을 보인다 |
| 진행 기간 배지 (`scheduled`~`due`), Timeline 예정 모드 | 제거 |
| 하루 용량 (`daily_capacity`, MCP `day_load`) | 제거. 예상 소요 없이는 계산할 수 없다 |
| 롤오버 (`tp rollover`, 기동 시 자동 이월) | 제거 |
| 주간 리포트 | "예상 N"·"마감" 표기 대신 착수일·걸린 기간·작업 시간 |

**기존 데이터.** 파일은 고치지 않는다. 기존 `due`·`estimate`·`rollover_count` 는
파싱해서 그대로 보존하고 상세 화면에 "이전 값"으로만 보인다. 질의 `due:` 는 과거 데이터
검색용으로 남긴다. 걷어낸 기능이 쓰던 config 키(`daily_capacity`, `due_soon_days`,
`auto_rollover`, `rollover_warn_at`)는 읽어도 무시하고 경고 한 줄을 낸다.

**버리는 것.** 예상 대비 실측으로 추정 감각을 교정한다는 목적(추가 기능 8번의 원래 뜻)을
버린다. 다시 필요해지면 예상치를 다시 받는 대신, 같은 프로젝트·태그의 과거 걸린 기간
중앙값을 보여주는 쪽으로 간다. 기록이 쌓여야 의미가 있으므로 지금 만들지 않는다.

**합격 기준.** 개정 반영 후 2주 동안 완료한 사람 작업 중 착수 기록(진행중 구간 10분
이상 또는 소급)이 있는 비율이 80% 이상. 못 미치면 기능을 더하지 않고 소급 질문이
어디서 건너뛰어지는지부터 본다(재검토 트리거 마지막 줄과 같은 원칙).

### 실행 agent 지정과 가져가기 (2026-10-03)

```yaml
agent: claude          # claude | codex | auto. 비우면 지정 없음
tier: deep             # fast | standard | deep. 비우면 실행하는 쪽이 판단
claimed_by: claude:7f40c4c3   # 가져간 실행. <agent>:<세션>
```

허용 agent 와 등급별 모델은 vault 의 `config.yaml` 한 곳에 둔다. TP 만 쓰는
세션과 나루가 같은 표를 읽어야 기준이 갈라지지 않는다.

```yaml
agents:
  allowed: [claude, codex]
  models:
    claude: {fast: haiku, standard: sonnet, deep: opus}
    codex:  {fast: gpt-6-luna, standard: gpt-6-sol, deep: gpt-6-astra}
```

- 허용 목록은 사람·장비마다 다르다(Claude 만, Codex 만, 장비별로 다름). 정하는 순서:
  ① 환경변수 `TP_AGENTS=codex`(이 장비, vault 설정을 교체) → ② `config.yaml` 의
  `agents.allowed`(이 사람의 vault) → ③ PATH 에서 찾은 `claude`·`codex` CLI →
  ④ 둘 다. ③은 설치만 볼 뿐 로그인은 모른다 — 정확히 하려면 ①이나 ②에 적는다.
  vault 는 git 으로 장비 사이를 오가므로 감지 결과는 `config.yaml` 에 기록하지 않는다.
  MCP `vault_info` 의 `agents_source` 가 어느 단계에서 정해졌는지 알려준다.
- 허용 밖의 agent 는 등록·수정·가져가기에서 거부한다. `auto` 는 "허용된
  누구든" 이다. 모델명은 결과에 함께 돌려줄 뿐 이 도구가 실행하지 않는다.
- `agent` 를 지정하면 `executor: agent` 가 된다. 실행 주체를 정한 일은 에이전트
  기록이다. 사람 작업으로 되돌리려면 `agent` 를 비운다.
- **가져가기(claim)** 는 열린 일을 `claimed_by` 에 기록하고 진행중으로 바꾼다.
  이미 다른 실행이 가져갔거나, `agent` 가 다른 agent 로 지정됐거나, 보류 중이면
  거부한다. vault 잠금 안에서 파일을 다시 읽고 판단하므로 두 세션이 같은 일을
  동시에 가져가지 못한다. 대기중으로 되돌리면 `claimed_by` 가 지워지고, 완료·취소는
  누가 했는지 기록으로 남긴다.
- 질의: `agent:claude`(정확히 일치), `agent:none`, `tier:deep`, `is:claimed`,
  `is:unclaimed`, `pick:claude`(claude 나 auto 로 지정되고 아직 아무도 가져가지
  않은 열린 일).

**두 사용 방식.** 같은 필드를 쓰고 데이터 이전이 없다.

| 단계 | TP 만 사용 | TP + 나루 |
|---|---|---|
| 등록 | `tp add --agent --tier`, TUI, MCP `task_add` | 같음. 나루 `/work` 가 단계를 나눠 같은 필드로 등록할 수도 있다 |
| `auto`·등급 판단 | 가져간 세션이 판단해 `tier` 와 이유를 남긴다 | 나루 정책이 판단해 기록한다 |
| 실행 | 열린 세션이 `task_claim` 으로 자기 몫을 가져간다 | 나루 위임 실행기가 승인 후 worktree 에서. 실행 직전 같은 claim 을 쓴다 |
| 승인 | 가져가는 행위 자체 | 위임마다 명시 승인 |

사람이 적은 `agent`·`tier` 가 우선이다. 나루는 비어 있거나 `auto` 일 때만 채운다.
나루 연동(같은 표 읽기, 위임 실행 전 claim, `/work` 연결 시 필드 기록, 사람이 적은 값 우선)은
나루 저장소에서 했다(2026-10-03, 나루 PR #1). 나루는 표를 `tp agents --json` 으로 읽는다.

#### tier 를 고르는 기준과 올리는 규칙 (2026-10-03)

같은 기준이 README "실행 agent 지정과 가져가기" 와 `skills/task-planner/SKILL.md`
"Choosing and raising the tier" 에 있다. 고칠 때는 세 곳을 함께 고친다.

1. **기준은 크기가 아니라 "틀렸을 때 알아챌 수 있는가"다.** 작업량·토큰이 아니라 검증 수단을
   본다. 테스트·빌드·정해진 출력처럼 객관적으로 확인되면 `fast`(국소·반복) 또는 `standard`.
   맞았는지 판단이 필요하면(설계, 원인 불명, 리뷰) `deep`. 기반 구조·보안·데이터에 닿으면
   `deep`, 또는 `standard` 구현 + `deep` 리뷰로 나눈다.
2. **올리는 조건은 두 가지다.** 같은 검증이 두 번 실패했거나, 리뷰가 구조적 문제를 지적했을
   때. `task_edit` 로 `tier` 를 한 단계 올리고 사유를 메모에 남긴다. 낮추지는 않는다 —
   범위가 작아졌으면 task 를 나눈다.
3. **역할로 나눈다.** 계획·리뷰는 `deep`, 그 계획대로 하는 구현은 `standard` 가 기본이다.
4. **상향 기록이 기본값을 고친다.** 같은 종류의 일이 반복해서 올라가면 처음부터 그 등급으로
   적는다. `tp list 'body:tier=deep'` 로 중간에 올라간 일을 모아 본다(수정 로그에 남는다).
5. **tier 는 위임할 때만 효력이 있다.** 메인 세션이 직접 구현하면 그 세션의 모델로 하고 tier
   와 무관하다. subagent 에 맡기거나 다른 세션이 `pick:` 으로 가져갈 때 그 실행의 모델이 된다.

### 프로젝트 = 디렉토리가 아니라 필드 참조

`projects/<slug>/project.md`에 프로젝트 메타를 두고, 태스크는 `project:` 필드로 참조한다. 태스크 파일을 프로젝트 디렉토리 아래 두지 않은 이유는 프로젝트 이동 시 파일 이동이 필요해지고, 다중 프로젝트 연관이 불가능해지기 때문이다. 탐색은 인덱스가 만든 뷰로 한다.

### 인덱스 = 파생물

`.index/index.json`에 전체 태스크의 frontmatter 요약과 각 파일의 mtime·hash를 담는다. 기동 시 mtime을 비교해 변경분만 재파싱한다. **인덱스는 언제 지워도 md에서 완전 재생성된다** — 이 불변식을 깨는 필드를 인덱스에만 두면 안 된다.

## DB 판단 — 지금은 넣지 않는다

질문에 대한 답이다.

**Docker Postgres: 이 단계에서는 순손실.** 이유는 성능이 아니라 기동 조건이다. 아침에 터미널 열고 2초 안에 오늘 할 일을 봐야 하는 도구가 Docker 데몬 기동 여부에 의존하면, 도커가 안 떠 있는 날 도구를 안 쓰게 된다. 한 번 안 쓰면 데이터가 낡고 낡으면 영영 안 쓴다. 개인 도구의 실패는 성능이 아니라 이 경로로 온다.

**SQLite도 P0에는 불필요.** 태스크 2,000건 기준 frontmatter 요약 JSON은 1~2MB 수준이고(추정, md 평균 1KB·요약 500B 가정) 전체 로드·파싱이 수십 ms다. 콜드스타트 100ms 목표 안에 들어간다.

**전환 트리거 — 아래 중 하나라도 걸리면 재검토한다.**

| 신호 | 전환 대상 |
|---|---|
| 인덱스 태스크 10,000건 초과, 또는 콜드스타트 300ms 초과 (실측 기준) | SQLite |
| 태스크 본문 전문 검색이 필요해짐 | SQLite + FTS5 |
| 집계 리포트 쿼리가 Go 코드로 감당 안 됨 | SQLite |
| 여러 기기에서 동시 쓰기, 또는 원격 서버 상주 | Postgres + 서버 아키텍처 재설계 |

SQLite로 가더라도 `modernc.org/sqlite`(cgo 불필요)를 쓰면 단일 바이너리 배포가 유지된다. **어느 경우에도 SQLite는 인덱스/캐시이고 md가 SSOT라는 관계는 유지한다.** 이 관계가 뒤집히면 md 관리라는 전제 자체가 무너진다.

## Rabbit holes — 미리 차단할 시간 낭비 지점

- **md 파서 직접 구현 금지.** frontmatter는 `goccy/go-yaml`, 본문은 필요해지면 `goldmark`. 자체 파서를 쓰기 시작하면 2주가 여기서 끝난다.
- **TUI 레이아웃 엔진 자작 금지.** Lipgloss가 제공하는 범위 안에서 화면을 설계한다.
- **P0에서 인덱스 증분 갱신 최적화 금지.** 2,000건 전체 재스캔이 100ms 안에 끝난다. 느려지면 그때 한다.
- **상태 워크플로우 커스터마이징 금지.** 5개 상태를 하드코딩한다. config로 뺄 수 있게 만들면 뷰·전이·통계가 전부 일반화돼야 한다.
- **동기화 직접 구현 금지.** git 커밋·푸시를 호출할 뿐 병합 로직을 만들지 않는다.

## 가정

작성자가 세운 전제다. 검증되면 갱신한다.

- 태스크 생성량 하루 5~15건, 연 2,000건 내외 **(추정, 실측 근거 없음)**
- md 파일 평균 1KB, frontmatter 요약 500B **(추정)**
- 동시 접근은 TUI 1 + CLI 간헐 + 에디터 1. 다중 세션 동시 쓰기는 없음
- vault는 git repo이며 백업은 원격 저장소에 의존
- 로컬 환경: go 1.25.11 darwin/arm64, Docker 29.4.0 (2026-09-12 확인)

## 재검토 트리거

- P0가 2주 안에 안 끝나면 → 범위를 Today 뷰 + 캡처 + 상태 전이로 더 줄인다
- 콜드스타트 300ms 초과 또는 태스크 10,000건 초과 → 인덱스 백엔드 재검토 (위 DB 절)
- 다중 기기 실시간 동기화 요구 발생 → 서버 아키텍처로 문서 신규 작성
- 7일 시범 사용에서 도구를 안 열게 되면 → 기능이 아니라 마찰 지점을 찾는다. 기능 추가로 대응하지 않는다
